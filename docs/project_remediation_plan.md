## TASK-001

### ID задачи
TASK-001

### Название задачи
Переработать dedupe-модель очереди задач

### Приоритет
Critical

### Тип задачи
Architecture

### Контекст проблемы
Сейчас dedupe для jobs основан на глобально уникальном `dedupe_key` в таблице `jobs`. Постановка задачи с тем же ключом повторно подавляется через `ON CONFLICT DO NOTHING`, даже если старая задача уже завершена или упала. Это касается как минимум `build_post_report`, `build_event_report`, `build_process_report`.

Проблема проявляется в job-пайплайне и напрямую ломает надежность orchestration. Автоматические каскадные пересборки могут перестать ставиться в очередь после первого исполнения, пока старые записи не будут удалены retention-процессом.

### Цель задачи
Сделать dedupe корректным для активных задач, но не блокирующим повторную постановку после завершения или отмены предыдущих запусков.

### Что нужно сделать
- Проанализировать текущую модель `jobs.dedupe_key` и места постановки задач.
- Убрать глобальную уникальность dedupe на всю историю задач.
- Реализовать один из допустимых вариантов:
  - dedupe только для `pending/running`;
  - отдельная таблица активных dedupe-locks;
  - очистка/освобождение `dedupe_key` при terminal state.
- Обновить enqueue-логику для `build_post_report`, `build_event_report`, `build_process_report`, `build_post_links`, `collect_comments`.
- Сохранить защиту от дубликатов в рамках активного исполнения.

### Технические требования
- Решение должно быть транзакционно безопасным.
- Нельзя допустить гонку, при которой две одинаковые активные задачи создаются параллельно.
- Нельзя привязывать корректность к retention-джобам.
- Обработку ошибок и rollback нужно сохранить.

### Ожидаемый результат
Одинаковая задача не может быть продублирована во время активного исполнения, но может быть поставлена повторно после завершения предыдущего запуска.

### Критерии готовности (Definition of Done)
- Повторная постановка `build_post_report:{post_id}` после `done` или `failed` успешно создает новую задачу.
- Во время `pending/running` повторная постановка дубликата подавляется.
- Добавлены интеграционные тесты на dedupe lifecycle.
- Нет регрессии для существующих API enqueue flows.

### Контекст проблемы

### Цель задачи
Перевести сборку событий на idempotent update-модель, где события сохраняют идентичность, а изменения применяются как diff к membership и метаданным.

### Что нужно сделать
- Проанализировать current rebuild flow для `Event` и `EventPost`.
- Определить стабильный identity strategy для событий.
- Заменить полный delete/recreate на:
  - поиск существующих событий-кандидатов;
  - пересчет membership;
  - обновление `started_at`, `ended_at`, `title`, `confidence`, `status`;
  - удаление только устаревших membership, а не сущности целиком.
- Пересмотреть отношение отчетов и rebuild, чтобы старые `event_report` не уничтожались cascade-удалением сущности.

### Технические требования
- Нельзя ломать внешние ссылки на `event_id`.

### Ожидаемый результат
События сохраняют `id` между пересборками, membership обновляется без полной потери сущности, отчеты и связанные процессы не уничтожаются каскадом.

### Критерии готовности (Definition of Done)
- Повторный rebuild на том же наборе постов не создает новый `event_id`.
- Изменение состава постов обновляет membership существующего события.
- Старые `event_report` не теряются из-за удаления `Event`.
- Добавлены integration-тесты на сохранение identity события.
