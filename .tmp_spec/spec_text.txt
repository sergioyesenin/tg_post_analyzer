СПЕЦИФИКАЦИЯ МУЛЬТИАГЕНТНОЙ СИСТЕМЫ АНАЛИЗА НОВОСТЕЙ v2 (стабилизированная)
1. Назначение системы
Система формирует аналитический отчет по новостному событию на основе:
текста статьи;
пользовательских комментариев;
внешних источников (при необходимости).
Выход системы
аналитический текст (5–7 предложений);
структурированные данные для downstream;
внутренние трассы анализа (internal only).
2. Ключевые принципы
2.1. Аналитическая ценность (формализовано)
Отчет считается валидным, если содержит:
Компонент
Обязательность
Факт события
обязательно
Контекст/предпосылки
обязательно
Общественная реакция
обязательно (или явно указана недостаточность)
Интерпретация
обязательно
Последствия
обязательно
Дополнительно:
текст ≠ пересказ статьи;
есть различение факт / интерпретация / прогноз.
2.2. Контролируемая интерпретация
Каждое утверждение относится к типу:
fact — прямо из входных данных;
derived — логический вывод;
external — из retrieval;
uncertain — при недостатке данных.
2.3. Объяснимость
Каждый блок анализа:
имеет источник;
имеет confidence;
может быть трассирован через pipeline.
2.4. Итеративная верификация
Pipeline включает reviewer loop с ограничениями:
max_iterations: 2
total LLM calls budget: ограничен runtime
обязательная остановка при:
достижении accept;
исчерпании лимита;
insufficient_data.
2.5. Семантический анализ (обязателен)
Запрещено:
использовать keyword matching как основной сигнал.
Разрешено:
использовать keywords только как вспомогательный feature.
## 3. Epistemic Model (формализованная модель знания)
### 3.1 Назначение
Epistemic Model определяет:
- какие типы утверждений может делать система;
- какие выводы допустимы;
- где проходит граница между анализом и галлюцинацией;
- как классифицируются все элементы знания в pipeline.
Эта модель обязательна для:
- Expert Agent
- Synthesis Agent
- Reviewer Agent
---
## 3.2 Типы утверждений (обязательная классификация)
Каждое утверждение в системе должно относиться к одному из типов:
### 1. fact
Факт, напрямую извлеченный из входных данных:
- статья
- комментарии
- retrieval источники
❗ Запрещено изменять смысл факта.
---
### 2. external
Факт, полученный из внешнего источника (retrieval).
Требования:
- должен иметь источник;
- не может противоречить другим external данным без пометки.
---
### 3. derived
Логический вывод, построенный на основе:
- одного или нескольких фактов;
- без добавления новой информации.
Примеры:
- обобщение повторяющихся комментариев;
- выявление паттерна.
---
### 4. interpretation
Объяснение значения или контекста события.
Характеристики:
- связывает факты между собой;
- объясняет “что это означает”;
- не утверждает новых фактов.
❗ Интерпретация не должна вводить новые сущности или события.
---
### 5. consequence
Оценка возможных эффектов события.
Требования:
- должна опираться на:
- факты;
- интерпретацию;
- не должна быть спекулятивной без основания.
---
### 6. forecast
Гипотетический сценарий будущего.
Разрешен только если:
- есть явное основание;
- есть подтверждение из external или repeated patterns.
---
### 7. uncertain
Используется если:
- данных недостаточно;
- вывод не может быть подтвержден.
---
## 3.3 Допустимые логические переходы
Система может строить выводы только по следующим цепочкам:
- fact → derived
- fact → interpretation
- external → interpretation
- interpretation → consequence
- consequence → forecast (ограниченно)
❗ Запрещенные переходы:
- fact → forecast (без промежуточных шагов)
- комментарий → факт
- single comment → общественное мнение
- interpretation → fact
---
## 3.4 Правила интерпретации
Интерпретация допускается только если:
1. Есть достаточная опора:
- ≥2 независимых факта
ИЛИ
- факт + external подтверждение
2. Интерпретация не:
- добавляет новые события;
- вводит скрытые мотивы без основания;
- утверждает причинность без явных признаков.
---
## 3.5 Правила построения общественного мнения
Общественная реакция может быть сформирована только если:
- есть повторяемость тезисов;
- комментарии содержательные;
- отсутствует сильный шум.
❗ Запрещено:
- делать вывод из единичных комментариев;
- обобщать “все считают”.
---
## 3.6 Правила работы с конфликтами данных
Если данные противоречат:
- при conflict внутри статьи → использовать факт как есть без интерпретации;
- при conflict между external источниками → отметить как uncertain;
- при conflict между комментариями → считать discussion_state = conflicted.
---
## 3.7 Определение галлюцинации
Галлюцинацией считается:
- добавление факта, отсутствующего во входных данных;
- утверждение причинности без опоры;
- использование внешних знаний без retrieval;
- выдача интерпретации как факта.
---
## 3.8 Confidence Model (эпистемический)
Уровень уверенности зависит от источника:
| Тип | Confidence |
|-----|----------|
| fact (article) | высокий |
| external | высокий (если источник надежный) |
| derived | средний |
| interpretation | средний |
| consequence | низкий-средний |
| forecast | низкий |
---
## 3.9 Обязательное требование
Каждый агент обязан:
- явно или неявно соблюдать эту модель;
- не смешивать типы утверждений;
- передавать downstream корректную структуру знания.
Reviewer обязан:
- проверять соблюдение этой модели.Все элементы в:- background- interpretations- consequencesдолжны иметь структуру:{"text": "","type": "fact|derived|interpretation|external|uncertain","confidence": 0.0,"source": "article|comments|retrieval"}
3. Архитектура pipeline
Последовательность:
Context → Routing → Expert → Public Opinion → Synthesis → Reviewer
Выполнение:
внутри одного job;
без создания новых runtime агентов;
с возможностью rerun отдельных веток.

## 5. Data Sufficiency Model (формализованная модель достаточности данных)
### 5.1 Назначение
Модель определяет:
- достаточно ли данных для анализа;
- какого типа недостаточность присутствует;
- как система должна реагировать на ограничения.
❗ Важно: недостаточность данных НЕ является единой шкалой.
Она состоит из независимых компонентов.
---
## 5.2 Типы достаточности (разделены)
Система оценивает отдельно:
### 1. Article Sufficiency
Достаточность самой статьи.
Оценивается по:
- наличию четкого события;
- наличию субъектов;
- наличию действия;
- связности текста.
---
### 2. Comment Sufficiency
Достаточность пользовательских комментариев.
Оценивается по:
- количеству;
- содержательности;
- разнообразию мнений;
- уровню шума.
---
### 3. Retrieval Sufficiency
Достаточность внешнего контекста.
Оценивается по:
- наличию релевантных источников;
- согласованности источников;
- полноте контекста.
---
### 4. Analytical Sufficiency
Способность построить связный анализ.
Оценивается по:
- возможности собрать 5 компонентов;
- наличию причинно-следственных связей;
- отсутствию логических разрывов.
---
## 5.3 Уровни достаточности (локальные)
Каждый тип получает статус:
- `sufficient` — данных достаточно;
- `limited` — можно продолжать с ограничениями;
- `weak_signal` — данные есть, но слабые;
- `insufficient` — данных недостаточно.
---
## 5.4 Агент-специфичное использованиеКаждый агент использует модель достаточности по-разному.---### Context AgentИспользует:- Article SufficiencyПравила:- если insufficient → pipeline останавливается;- если limited → допускается, но снижает confidence downstream.---### Routing AgentИспользует:- Article Sufficiency (косвенно)Правила:- если Article Sufficiency = limited → routing confidence снижается;- если insufficient → routing не выполняется;- передает retrieval_hints downstream, но не принимает окончательное retrieval-решение.---### Expert AgentИспользует:- Article Sufficiency- Retrieval SufficiencyПравила:- если Retrieval Decision Model определил retrieval как required и Retrieval Sufficiency = insufficient → статус limited;- если Article Sufficiency = limited → интерпретации ограничены;- не имеет права усиливать слабые данные.---### Public Opinion AgentИспользует:- Comment SufficiencyПравила:- sufficient → полноценный анализ;- weak_signal → допускается с оговорками;- insufficient → реакция помечается как отсутствующая.---### Synthesis AgentИспользует:- Analytical Sufficiency- агрегированные статусы всех предыдущих агентовПравила:- если Analytical Sufficiency = insufficient → отчет невозможен;- если limited → текст обязан явно отражать ограничения;- обязан корректно интегрировать слабые сигналы.---### Reviewer AgentИспользует:- ВСЕ типы sufficiencyПравила:- проверяет корректность использования sufficiency;- выявляет:- игнорирование слабых данных;- ложную уверенность;- отсутствие ограничений в тексте;- инициирует rerun при misuse;- может завершить pipeline с `insufficient_data`.---
## 5.5 Правила агрегации
Финальный статус определяется по приоритету:
1. если Article Sufficiency = insufficient → итог: insufficient_data
2. если Analytical Sufficiency = insufficient → итог: insufficient_data
3. если есть хотя бы один `limited` → итог: limited
4. если есть `weak_signal` (только комментарии) → итог: limited
5. иначе → sufficient
---
## 5.6 Поведение pipeline
### sufficient
- полный анализ
- все компоненты обязательны
---
### limited
- анализ допускается
- обязательны:
- событие
- интерпретация
- последствия
- допускается:
- слабая реакция
- ограниченный контекст
---
### weak_signal
- используется только для комментариев
- не влияет на остановку pipeline
- влияет на формулировки (должны быть мягче)
---
### insufficient_data
- pipeline останавливается
- возвращается:
- error
ИЛИ
- минимальный fallback (опционально)
---
## 5.7 Правила обязательного поведения
Система обязана:
- явно учитывать слабость данных;
- НЕ скрывать недостаточность;
- НЕ усиливать слабые сигналы до уверенных выводов.
---
## 5.8 Влияние на текст отчета
Если статус ≠ sufficient:
- должны появляться маркеры:
- “по имеющимся данным”
- “ограниченная реакция”
- “недостаточно информации”
---
## 5.9 Связь с Reviewer
Reviewer обязан:
- проверять корректность оценки sufficiency;
- выявлять:
- ложные уверенные выводы;
- игнорирование weak_signal;
- инициировать rerun при misuse.

6.1 Context Agent

### 6.2 Routing Agent (формализованная модель)
#### Назначение
Определить аналитическую категорию события и требования к внешнему контексту.
Routing НЕ принимает решения о retrieval.
Routing передает признаки:
- actor_type
- context_type
- scale
Retrieval Decision Model — единственный источник истины.
---
## 6.2.1 Категории (строгие определения)
Категория определяется по **типу доминирующего объяснительного контекста**, а не по ключевым словам.
### politics
События, в которых:
- главный актор — государство, международная организация или политический субъект;
- действие связано с регулированием, санкциями, заявлениями, международными отношениями;
- последствия носят институциональный или межгосударственный характер.
---
### economy
События, где:
- основной контекст — рынок, финансы, бизнес;
- акторы — компании, финансовые структуры;
- последствия выражаются в экономических изменениях.
---
### crisis
События, где:
- присутствует резкое нарушение нормального функционирования;
- есть ущерб, риск, авария, сбой;
- последствия носят срочный или дестабилизирующий характер.
---
### tech
События, где:
- основной контекст — технологии или продукты;
- изменения носят функциональный или инновационный характер;
- нет доминирующего политического или кризисного аспекта.
---
### social
События, где:
- основной фокус — общество, поведение людей, социальные реакции;
- отсутствует доминирующий институциональный или экономический контекст.
---
### mixed
Используется только если:
- присутствуют **два или более равнозначных контекста**;
- ни один не доминирует.
Использование `mixed`:
- должно быть обосновано;
- не должно использоваться как fallback при неуверенности.
---
## 6.2.2 Признаки классификации
Routing анализирует следующие признаки:
1. Тип главного актора
2. Тип действия (регулирование, рынок, сбой, реакция)
3. Масштаб последствий (локальный / системный / международный)
4. Характер контекста (институциональный / экономический / технический / социальный)
5. Тональность события (стабильность / нарушение / развитие)
---
## 6.2.3 Приоритет признаков
При конфликте используется следующий приоритет:
1. Тип главного актора
2. Характер действия
3. Масштаб последствий
4. Контекст
5. Тональность
---
## 6.2.4 Алгоритм выбора категории
1. Определить главного актора.
2. Определить характер действия.
3. Определить основной контекст.
4. Проверить, есть ли доминирующий контекст:
- если да → выбрать категорию;
- если нет → проверить условия `mixed`.
5. Проверить, не является ли выбор следствием неопределенности:
- если да → снизить confidence, но не использовать `mixed`.
---
## 6.2.5 Уровень уверенности
- высокий: признаки согласованы;
- средний: есть слабые противоречия;
- низкий: признаки конфликтуют.
---
## 6.2.6 Передача признаков для RetrievalRouting Agent обязан выделять признаки, влияющие на Retrieval Decision Model:- institutional_context- international_context- external_context_missing- high_error_costЭти признаки:- не являются окончательным retrieval-решением;- передаются downstream;- используются Retrieval Policy как входные сигналы.
---

Вход:

Output:

Правила:

Expert Agent использует единый базовый epistemic режим для всех новостей, но обязан адаптировать аналитический фокус в зависимости от категории, определенной Routing Agent.
❗ Категория влияет:
- на приоритет анализа;
- на допустимые типы последствий;
- на уровень осторожности интерпретации;
- на требования к внешнему контексту.
❗ Категория НЕ влияет:
- на JSON-структуру output;
- на Epistemic Model;
- на базовые правила против галлюцинаций.

#### politics
Основной аналитический фокус:
- институциональный контекст;
- действия государственных и политических акторов;
- международные, регуляторные и межгосударственные последствия.
Expert должен:
- проверять, требует ли событие внешнего контекста для корректной интерпретации;
- отделять факт политического действия от его значения;
- осторожно формулировать последствия, если нет внешнего подтверждения.
Запрещено:
- приписывать скрытые мотивы акторам без основания;
- усиливать конфликтность события без опоры;
- автоматически трактовать официальное заявление как доказанный долгосрочный тренд.
---
#### economy
Основной аналитический фокус:
- экономический контекст;
- влияние на компании, рынок, финансы, регуляторную среду;
- непосредственные и среднесрочные экономические последствия.
Expert должен:
- различать факт рыночного/корпоративного события и его интерпретацию;
- отделять локальные бизнес-эффекты от широких системных выводов;
- использовать осторожные формулировки для макроэкономических последствий.
Запрещено:
- выводить крупные системные эффекты без внешнего контекста;
- выдавать корпоративное событие за общеэкономический тренд без основания.
---
#### crisis
Основной аналитический фокус:
- нарушение нормального состояния;
- непосредственные риски;
- масштаб ущерба, сбоя или дестабилизации;
- срочность и ограниченность информации.
Expert должен:
- приоритизировать проверяемые факты о сбое, ущербе и рисках;
- явно учитывать, что кризисные данные часто неполны;
- ограничивать интерпретацию при дефиците подтверждений.
Запрещено:
- преувеличивать масштаб события;
- делать дальние прогнозы без достаточной опоры;
- выдавать ранние неполные данные за устойчивую картину.
---
#### tech
Основной аналитический фокус:
- технологический или продуктовый контекст;
- функциональные изменения;
- ограничения технологии;
- практический эффект для пользователей, систем или рынка.
Expert должен:
- отделять описание технологии от ее интерпретации;
- анализировать влияние на продукт, инфраструктуру или внедрение;
- не подменять tech-анализ политическим или кризисным, если это не подтверждено доминирующим контекстом.
Запрещено:
- делать широкие социальные или политические выводы без основания;
- трактовать любое техническое изменение как стратегический перелом.
---
#### social
Основной аналитический фокус:
- общественная реакция;
- поведенческие эффекты;
- восприятие события;
- социальная значимость и возможные общественные последствия.
Expert должен:
- учитывать общественный контекст, но не подменять им фактологическую основу;
- различать наблюдаемую реакцию и интерпретацию общественного значения;
- особенно осторожно относиться к representativeness комментариев.
Запрещено:
- выдавать реакцию комментариев за общественное мнение в широком смысле;
- строить сильные выводы о социальной значимости без достаточной базы.
---
#### mixed
Основной аналитический фокус:
- явное разделение двух или более доминирующих аспектов;
- объяснение того, как они связаны;
- недопущение схлопывания нескольких контекстов в один.
Expert должен:
- сначала разложить событие на отдельные контуры анализа;
- затем описать их взаимосвязь;
- избегать размытых универсальных формулировок.
Запрещено:
- использовать mixed как оправдание неопределенности;
- писать обобщенный анализ без явного разделения аспектов.
---
### 6.3.2 Rule of Category Priority
Если category определена, Expert обязан использовать соответствующую analytical guidance как primary frame анализа.
Если category = mixed:
- Expert обязан явно отразить минимум два аналитических контура;
- один из них не может быть скрыт внутри общего описания.
Если данные статьи противоречат category guidance:
- приоритет имеют факты статьи и Epistemic Model;
- category guidance используется как рамка интерпретации, а не как источник фактов.
6.4 Public Opinion Agent
{  "discussion_state": "...",  "main_topics": [...],  "dominant_reactions": [...],  "data_status": "sufficient|limited|weak_signal"}### 6.4.1 Правила анализа общественной реакции
Public Opinion Agent анализирует не отдельные комментарии, а структуру обсуждения.
Обязательные шаги анализа:
1. Очистить шум:
- игнорировать флуд;
- игнорировать оффтоп;
- игнорировать личные перепалки без отношения к событию.
2. Выделить релевантные комментарии:
- учитывать только комментарии, связанные с событием;
- учитывать только содержательные комментарии.
3. Определить повторяемые тезисы:
- тезис считается повторяемым, если он выражен более чем в одном независимом комментарии;
- единичный комментарий не может определять dominant reaction.
4. Выявить структуру обсуждения:
- supportive — преобладает поддержка;
- critical — преобладает критика;
- mixed — присутствуют разные позиции без выраженного конфликта;
- conflicted — позиции не только различаются, но и вступают в активное столкновение;
- weak_signal — комментариев недостаточно для уверенного вывода.
---
### 6.4.2 Минимальные требования к достаточности
Comment Sufficiency считается:
- `sufficient`, если есть достаточно содержательных и релевантных комментариев для выделения повторяемых тезисов;
- `weak_signal`, если комментарии есть, но:
- их мало;
- они слабо содержательны;
- нет устойчивых повторяемых тезисов;
- `insufficient`, если комментарии отсутствуют или полностью нерелевантны событию.
---
### 6.4.3 Ограничения
Public Opinion Agent запрещено:
- делать вывод о dominant reaction по одному комментарию;
- выдавать реакцию комментариев за общественное мнение в широком смысле;
- усиливать слабый сигнал до уверенного вывода;
- подменять анализ реакции пересказом статьи.
---
### 6.4.4 Output interpretation rules
- `main_topics` должны отражать именно темы обсуждения, а не просто сущности статьи;
- `dominant_reactions` должны содержать только повторяемые и достаточно обоснованные реакции;
- при `weak_signal` агент обязан явно снижать уверенность;
- при `insufficient` агент обязан возвращать отсутствие надежной реакции, а не искусственно заполнять output.

## 7.7 Обязательные проверки Reviewer
Reviewer обязан проверить:
### 1. Component coverage
- все 5 компонентов присутствуют:
- событие
- контекст
- реакция
- интерпретация
- последствия
---
### 2. Mapping correctness
- `summary` соответствует событию;
- `topics` отражают содержание события, а не только комментарии;
- `confidence` соответствует sufficiency и не завышен;
- `status` согласован с реальным качеством и полнотой данных.
---
### 3. Non-summarization
- текст не является пересказом статьи;
- текст содержит аналитическую добавленную ценность.
---
### 4. Epistemic correctness
- нет новых фактов без источника;
- нет смешения типов утверждений;
- интерпретации не выдаются как факты.
---
### 5. Evidence grounding
- все ключевые выводы опираются на:
- статью;
- комментарии;
- retrieval (если применимо).
---
### 6. Logical consistency
- нет противоречий между частями;
- нет противоречий между ветками:
- context vs synthesis;
- expert vs public_opinion;
- retrieval evidence vs final interpretation.

## 8. Retrieval Policy (формализованная модель внешнего контекста)### 8.1 НазначениеRetrieval используется для:- дополнения контекста статьи;- повышения точности интерпретации;- снижения риска ошибок в аналитике.❗ Retrieval НЕ используется:- для генерации новых фактов без проверки;- как основной источник анализа;- как замена статьи.---## 8.2 Принцип использованияRetrieval применяется только если:👉 без внешнего контекста невозможно:- корректно объяснить событие;- оценить последствия;- избежать ошибочной интерпретации.---## 8.3 Decision Model (независим от категории)Retrieval_required = true если выполняется хотя бы одно:1. Событие имеет:   - международный контекст;   - межгосударственные последствия;2. В статье:   - отсутствует ключевой контекст;   - есть ссылки на внешние события без объяснения;3. Интерпретация требует:   - исторического контекста;   - внешнего подтверждения;4. Цена ошибки высокая:   - политические заявления;   - санкции;   - кризисные ситуации.---Retrieval_required = false если:- статья самодостаточна;- событие локальное;- интерпретация не зависит от внешних данных.---## 8.4 Типы источниковИсточники классифицируются:### Tier 1 (надежные)- официальные сайты- государственные органы- международные организации---### Tier 2 (доверенные)- крупные СМИ- известные аналитические ресурсы---### Tier 3 (ограниченные)- агрегаторы- блоги- вторичные источники---Правила:- предпочтение Tier 1 → Tier 2 → Tier 3- нельзя строить вывод только на Tier 3---## 8.5 Ограничения retrieval- max_sources: 3- timeout: ограничен runtime- обязательна дедупликация- запрещено использовать нерелевантные источники---## 8.6 Evidence ModelКаждый источник оформляется как:```json{  "title": "",  "source": "",  "tier": "1|2|3",  "supports": "",  "relevance": 0.0}
Требования:
должен указывать, какое утверждение поддерживает (supports);
должен быть релевантен текущему событию;
должен быть согласован с другими источниками.
8.7 Работа с конфликтующими источниками
Если источники противоречат:
не выбирать один как “истину”;
помечать как uncertain;
снижать confidence;
использовать формулировки:
“данные различаются”
“нет единой оценки”
8.8 Failure handling
Retrieval failed (timeout / error):
НЕ останавливает pipeline;
устанавливает Retrieval Sufficiency = insufficient;
переводит Expert в режим limited.
Retrieval пустой:
трактуется как insufficient;
запрещено придумывать контекст.
## 8.9 Влияние на Expert Agent
Expert обязан:
- использовать retrieval, если Retrieval Decision Model определил его как required;
- не игнорировать retrieval data;
- не добавлять external факты без retrieval evidence.
Если Retrieval Decision Model определил retrieval как required, но Retrieval Sufficiency = insufficient:
- Expert status = limited;
- интерпретации должны быть ограничены;
- confidence не может быть высоким.
Если retrieval_required = true и не выполнен:
статус = limited;
интерпретации должны быть ограничены.
8.10 Влияние на Synthesis
Если retrieval использовался:
это должно быть отражено неявно в тексте;
не должно появляться “магических знаний” без источника.
8.11 Влияние на Reviewer
Reviewer проверяет:
использован ли retrieval при необходимости;
есть ли unsupported external claims;
есть ли конфликт источников;
корректно ли обработан insufficient retrieval.
8.12 Запрещенные практики
придумывать external факты;
использовать “знания модели” без источников;
усиливать интерпретации за счет несуществующих данных;
использовать retrieval как основной источник анализа.

## 9. Mapping Internal → Public Report (контракт преобразования)
### 9.1 Назначение
Этот раздел определяет:
- как результаты multi-agent pipeline преобразуются в `post_report_v2`;
- какие данные являются публичными;
- какие данные остаются внутренними;
- как сохраняется совместимость с текущим API.
❗ Важно:
- mapping НЕ является прямым копированием;
- mapping выполняет нормализацию и адаптацию данных;
- mapping гарантирует стабильность публичного контракта.
---
## 9.2 Принципы преобразования
### 1. Contract preservation
- все обязательные поля `post_report_v2` должны сохраняться;
- структура API не должна ломаться.
---
### 2. Semantic stability
- смысл полей должен оставаться максимально близким к текущему;
- если смысл меняется → это должно быть явно задокументировано.
---
### 3. Controlled degradation
- при `limited` данные ослабляются, но не заменяются;
- при `insufficient_data` возвращается fallback.
---
### 4. No leakage
- internal данные (`meta.multi_agent`) не попадают в публичный API.
---

- событие
- контекст
- реакцию (или указание на ее слабость)
- интерпретацию
- последствия
- при `limited`:
- должны быть маркеры ограниченности.
---
### topics
Источник:
- комбинация:
- context.entities
- public_opinion.main_topics
Правила:
- не должны зависеть только от комментариев;
- должны отражать содержание события;
- должны быть нормализованы (без дублей).
---
### confidence
Источник:
- агрегированное значение из:
- synthesis.confidence
- expert.confidence
- public_opinion.confidence
---
Правила расчета:
- если есть `limited` → confidence снижается;
- если есть `weak_signal` → дополнительное снижение;
- если есть conflicts → снижение;
- не может быть высоким при наличии ограничений.
---
### status
Источник:
- финальный статус из Data Sufficiency Model
---
Возможные значения:
- `ready`
- `limited`
- `insufficient_data`
---
## 9.4 Правила агрегирования confidence
Примерная модель:
- base = synthesis.confidence
- если expert = limited → base * 0.8
- если public_opinion = weak_signal → base * 0.9
- если retrieval conflict → base * 0.7
(точные коэффициенты могут быть настроены)
## 9.4.1 Ограничения confidence (обязательные)
Confidence не является произвольным значением и должен подчиняться правилам:
---
### Запрещено:
- высокий confidence при:
- status = limited
- наличии конфликтов данных
- weak_signal
- отсутствии retrieval при required
---
### Обязательные зависимости:
Confidence должен снижаться если:
- есть Retrieval conflict
- есть противоречия между ветками
- часть компонентов построена на limited данных
- используется uncertain утверждение
---
### Минимальные правила:
- sufficient → допускается высокий confidence
- limited → максимум средний
- insufficient_data → низкий
---
Нарушение этих правил считается defect D4 (data misuse).
---
## 9.5 Поведение при insufficient_data
Если:
- Article Sufficiency = insufficient
ИЛИ
- Analytical Sufficiency = insufficient
Тогда:
- status = insufficient_data
- content:
- краткое описание события (если возможно)
- указание на недостаточность данных
- topics = []
- confidence = низкий
---
## 9.6 Поведение при limited
Если статус = limited:
- content должен явно отражать ограничения;
- запрещено:
- писать уверенные выводы;
- скрывать слабость данных.
---
## 9.7 Гарантии совместимости
Система обязана:
- не изменять:
- названия полей
- обязательность полей
- не менять типы данных;
- не вводить новые обязательные поля.
---
## 9.8 Запрещенные практики
- прямое копирование internal структуры в API;
- использование только комментариев для topics;
- завышение confidence;
- генерация “уверенного” текста при limited;
- добавление новых полей без versioning.
---
## 9.9 Влияние на downstream системы
Mapping должен гарантировать:
- event/process aggregation продолжает работать;
- frontend корректно отображает данные;
- экспорт/reporting не ломается.
---
## 9.10 Ответственность Reviewer
Reviewer обязан проверить:
- корректность mapping;
- отсутствие semantic drift;
- соответствие status и content;
- соответствие confidence реальному уровню данных.
## 10. Failure / Fallback Policy (формализованная схема отказоустойчивости)
### 10.1 Назначение
Этот раздел определяет:
- как система ведет себя при сбоях, недостатке данных и исчерпании итераций;
- когда допускается partial output;
- когда обязателен insufficient_data;
- как должен выглядеть fallback результат.
---
## 10.2 Типы отказов
Система различает:
### F1. Data failure
Недостаточно данных во входе:
- статья не позволяет выделить событие;
- комментарии отсутствуют или нерелевантны;
- retrieval не дал usable context.
---
### F2. Model failure
Модель не смогла выдать корректный ответ:
- invalid JSON;
- нарушение обязательной структуры;
- пустой или неинформативный output.
---
### F3. Retrieval failure
Внешний контекст required, но:
- timeout;
- network error;
- пустой результат;
- конфликтующие источники без usable consensus.
---
### F4. Review exhaustion
Reviewer loop исчерпан, но accept не достигнут.
---
## 10.3 Приоритет обработки отказов
1. Если Article Sufficiency = insufficient → terminal insufficient_data
2. Если Analytical Sufficiency = insufficient → terminal insufficient_data
3. Если retrieval failed, но статья позволяет ограниченный анализ → limited fallback
4. Если reviewer exhausted, но есть schema-valid result → partial limited result
5. Если model failure и retry budget не исчерпан → retry
6. Если model failure и retry budget исчерпан → insufficient_data или partial fallback по правилам ниже
---
## 10.4 Допустимые финальные режимы
### ready
Полный валидный анализ.
---
### limited
Анализ возможен, но есть ограничения:
- слабая реакция;
- недостаточный внешний контекст;
- ограниченные последствия;
- частичная неопределенность.
---
### insufficient_data
Корректный анализ невозможен.
---
## 10.5 Partial fallback result
Partial fallback допустим только если одновременно:
- событие можно кратко идентифицировать;
- schema-valid output можно собрать;
- ограничения данных могут быть явно отражены.
В partial fallback:
- summary = краткий фактический event summary;
- content = краткий текст с указанием, что данных недостаточно для полного анализа;
- topics = [] или минимально надежный набор;
- confidence = низкий;
- status = limited или insufficient_data в зависимости от severity.
---
## 10.6 Когда partial fallback запрещен
Partial fallback запрещен если:
- событие не выделяется из статьи;
- контекст статьи внутренне противоречив;
- output не может быть приведен к schema-valid форме;
- система не может отделить факт от недостоверной интерпретации.
В этих случаях:
- возвращается insufficient_data.
---
## 10.7 Поведение при конкретных сценариях
### Нет комментариев
- Comment Sufficiency = weak_signal
- pipeline продолжается
- общественная реакция отражается как ограниченная или отсутствующая
---
### Retrieval failed при required
- Retrieval Sufficiency = insufficient
- Expert status = limited
- Synthesis обязан отразить ограниченность контекста
---
### Invalid JSON от модели
- выполняется retry в пределах budget
- при исчерпании budget → fallback по 10.3
---
### Reviewer loop exhausted
- система возвращает лучший schema-valid результат
- status не может быть ready
- допускается только limited или insufficient_data
---
## 10.8 Fallback output requirements
Любой fallback output обязан:
- сохранять публичный контракт;
- явно отражать ограничения;
- не содержать сильных интерпретаций без опоры;
- не завышать confidence.
---
## 10.9 Ответственность Reviewer
Reviewer обязан:
- проверять, допустим ли fallback;
- запрещать partial output при epistemic violation;
- проверять, что fallback не маскирует failure как ready.
11. Acceptance criteria системы
### 11.1 Проверяемые proxy-критерии приемки
Acceptance criteria должны интерпретироваться через следующие проверяемые признаки:
1. Структурная полнота
- итоговый `content` содержит 5 обязательных компонентов:
- событие;
- контекст;
- реакцию или явное указание на ее ограниченность;
- интерпретацию;
- последствия.
2. Корректность epistemic поведения
- в отчете отсутствуют новые факты без опоры;
- интерпретации не маскируются под факты;
- retrieval-факты не появляются без retrieval evidence.
3. Корректность limited / insufficient режимов
- при `limited` статус не может быть `ready`;
- при `insufficient_data` запрещен уверенный аналитический текст;
- при `weak_signal` общественная реакция отражается как ограниченная или отсутствующая.
4. Корректность retrieval behavior
- если Retrieval Decision Model требует retrieval, то должен быть retrieval attempt;
- если retrieval failed, это должно снижать status и confidence;
- при conflicting retrieval запрещено завышать уверенность.
5. Корректность mapping
- `summary` остается фактическим;
- `topics` не строятся только на комментариях;
- `confidence` согласован с sufficiency;
- `status` согласован с fallback policy.
6. Непересказность
- итоговый текст не должен состоять только из перефразированной статьи;
- минимум один фрагмент должен объяснять значение события;
- минимум один фрагмент должен описывать последствия.
---
### 11.2 Минимальный набор сценариев приемки
Система должна проходить минимум следующие сценарии:
1. Полный достаточный кейс
- статья достаточна;
- комментарии содержательны;
- retrieval при необходимости успешен;
- итоговый статус = `ready`.
2. Weak-signal comments case- статья достаточна;- комментарии слабы или малочисленны;- если все остальные компоненты достаточны, итоговый статус может быть `ready`, но общественная реакция должна быть явно отражена как ограниченная;- если слабость комментариев влияет на полноту общего анализа, итоговый статус должен быть `limited`.
3. Retrieval-required failure case
- статья требует внешнего контекста;
- retrieval неуспешен;
- итоговый статус не может быть `ready`;
- интерпретация ограничена.
4. Schema-valid partial fallback case
- полный анализ не достигнут;
- но событие идентифицируется и output остается schema-valid;
- итоговый статус = `limited` или `insufficient_data`.
5. Terminal insufficient_data case
- событие нельзя надежно выделить;
- output не должен маскировать это под полноценный анализ;
- итоговый статус = `insufficient_data`.
