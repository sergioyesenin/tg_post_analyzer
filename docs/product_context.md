# Контекст продукта

## Что это за продукт

`tg_post_analyzer` — это аналитическая система мониторинга Telegram-каналов.

Продукт:

- собирает данные из Telegram;
- строит агрегированные представления на уровнях `Posts`, `Events`, `Processes`;
- показывает детали сущностей, связи и графовый контекст;
- поддерживает генерацию отчетов;
- включает служебные инструменты для управления каналами, пользователями, настройками, jobs и мониторингом runtime.

## Основной пользователь

Основной пользователь продукта — `analyst`.

Именно для него сосредоточена основная ценность системы:

- анализ потока постов;
- выделение и исследование событий;
- исследование процессов;
- просмотр и генерация отчетов;
- дополнительный исследовательский анализ через `keyword graph`.

Дополнительные роли:

- `admin` — владелец системы и оператор платформы;
- `viewer` — пользователь с доступом только на чтение.

## Зачем пользователь приходит в продукт

Пользователь приходит в продукт, чтобы:

- быстро понять, что происходит в наблюдаемых Telegram-каналах;
- найти важные посты, события и процессы;
- провалиться в детали и связи между сущностями;
- получить аналитический отчет;
- проверить свежесть, полноту и качество данных;
- при необходимости администрировать источники данных и работу пайплайна.

## Полный список пользовательских сценариев

### 1. Аутентификация и вход

- гость открывает `/login`;
- пользователь входит по логину и паролю;
- пользователь восстанавливает сессию через refresh flow;
- пользователь выходит из системы;
- аутентифицированный пользователь попадает в рабочую область;
- пользователь с недостаточными правами получает `forbidden`.

### 2. Работа с dashboard posts

- аналитик открывает `/dashboard/posts`;
- аналитик видит агрегированный snapshot постов;
- аналитик применяет фильтры по дате;
- аналитик фильтрует по каналам;
- аналитик фильтрует по категориям;
- аналитик ограничивает выборку по лимиту;
- аналитик фильтрует по минимальному числу комментариев;
- аналитик фильтрует по статусу отчета;
- аналитик сортирует посты по комментариям;
- аналитик сортирует посты по дате;
- аналитик сортирует посты по просмотрам;
- аналитик сортирует посты по вовлеченности;
- аналитик читает KPI summary по постам;
- аналитик видит `generated_at`;
- аналитик видит `warnings`;
- аналитик продолжает работу при `partial=true`;
- аналитик открывает конкретный пост из списка;
- viewer открывает тот же экран в read-only режиме.

### 3. Детали поста

- пользователь открывает `/posts/:postId`;
- пользователь смотрит полные метаданные поста;
- пользователь читает preview и контент поста;
- пользователь смотрит число комментариев, просмотров и вовлеченность;
- пользователь открывает блок комментариев;
- пользователь открывает блок связей;
- пользователь открывает блок отчета;
- пользователь возвращается назад к списку постов;
- viewer просматривает детали без mutation-действий.

### 4. Работа с комментариями поста

- analyst/admin запускает обновление комментариев поста;
- система создает job на обновление комментариев;
- пользователь наблюдает pending/running статус задачи;
- пользователь дожидается завершения job;
- после завершения интерфейс обновляет детали поста;
- пользователь видит ошибку, если job завершилась неуспешно.

### 5. Отчет по посту

- пользователь проверяет, есть ли отчет по посту;
- пользователь видит статус отчета: `missing`, `pending`, `draft`, `ready`, `failed`;
- analyst/admin запускает генерацию отчета по посту;
- analyst/admin запускает обновление существующего отчета;
- система ставит операцию в job queue;
- пользователь отслеживает прогресс выполнения;
- после завершения пользователь читает готовый отчет;
- viewer видит существующий отчет, но не может его запускать или обновлять.

### 6. Работа с dashboard events

- аналитик открывает `/dashboard/events`;
- аналитик видит список событий;
- аналитик фильтрует события по дате;
- аналитик фильтрует события по статусу;
- аналитик фильтрует по каналам;
- аналитик фильтрует по категориям;
- аналитик фильтрует по минимальному числу комментариев;
- аналитик сортирует события по дате начала;
- аналитик сортирует события по комментариям;
- аналитик сортирует события по вовлеченности;
- аналитик сортирует события по числу постов;
- аналитик видит summary по событиям;
- аналитик выбирает событие в списке;
- аналитик изучает граф выбранного события;
- аналитик смотрит связанные посты;
- аналитик смотрит статус отчета по событию;
- аналитик продолжает работу даже при partial snapshot;
- viewer изучает те же данные без мутаций.

### 7. Детали события

- пользователь открывает `/events/:eventId`;
- пользователь просматривает канонические данные события;
- пользователь видит контекст графа;
- пользователь изучает связанные посты;
- пользователь переходит из события в корневой пост;
- пользователь возвращается обратно в dashboard событий;
- viewer использует экран только для исследования.

### 8. Отчет по событию

- analyst/admin видит статус отчета по событию;
- analyst/admin запускает генерацию draft-отчета;
- analyst/admin обновляет draft-отчет;
- система ставит задачу в jobs flow;
- пользователь следит за прогрессом job;
- после завершения пользователь видит обновленный статус и содержимое отчета;

- аналитик сортирует процессы по вовлеченности;

- аналитик выбирает процесс;

- аналитик смотрит связанные события;
- аналитик переходит из процесса в событие;
- аналитик переходит из процесса в постовый контекст;
- аналитик проверяет статус process report;

- пользователь открывает `/processes/:processId`;
- пользователь просматривает канонические данные процесса;
- пользователь видит иерархический граф;
- пользователь изучает связанные события;
- пользователь переходит в связанные события и посты;
- пользователь возвращается в список процессов.

### 11. Отчет по процессу

- analyst/admin проверяет статус process report;
- analyst/admin запускает генерацию draft-отчета по процессу;
- analyst/admin обновляет process report;
- система исполняет задачу через jobs flow;
- пользователь отслеживает job status;
- после завершения пользователь получает обновленный отчет.

### 12. Каталоги отчетов

- пользователь открывает `/reports/posts`;
- пользователь открывает `/reports/events`;
- пользователь открывает `/reports/processes`;

- пользователь переходит из каталога к связанной сущности;
- пользователь экспортирует отчеты;
- viewer читает каталоги в read-only режиме.

### 13. Пакетная генерация отчетов по постам

- analyst/admin открывает каталог отчетов по постам;
- пользователь задает фильтры;
- пользователь запускает batch generation draft reports;
- система создает пакетную job;
- пользователь отслеживает ход пакетной задачи;
- после завершения обновляется список отчетов;
- пользователь проверяет, какие отчеты сгенерированы успешно, а какие нет.

### 14. Keyword graph как advanced research tool

- analyst/admin открывает `/keyword-graph`;
- пользователь вводит поисковый запрос;
- пользователь добавляет фильтры по каналам и датам;
- пользователь запускает поиск по постам;
- пользователь получает список найденных постов;
- пользователь выбирает seed posts для построения графа;
- пользователь строит граф связей по результатам поиска;
- пользователь изучает nodes и edges;
- пользователь использует граф как исследовательский инструмент;
- пользователь генерирует AI-отчет по графу;
- пользователь сравнивает результаты поиска и построенного графа;
- viewer не имеет доступа к этому модулю.

- admin открывает `/channels`;
- admin видит список каналов;
- admin добавляет новый канал;
- система создает асинхронную job на подключение канала;
- admin отслеживает статус этой job;
- admin редактирует данные канала;
- admin включает канал;
- admin отключает канал;
- admin удаляет канал;
- admin проверяет, какие каналы активны для ingest-пайплайна.

- admin видит список пользователей;
- admin создает нового пользователя;
- admin назначает роли пользователю;
- admin меняет роли существующему пользователю;
- admin активирует пользователя;
- admin деактивирует пользователя;
- admin контролирует доступ к аналитическим и административным контурам.

- admin открывает `/settings`;

- пользователь просматривает effective settings;
- admin редактирует отдельные настройки;
- admin сохраняет изменения;
- пользователь проверяет, как настройки влияют на поведение системы;
- analyst использует экран как справочный источник по текущей конфигурации.

- admin открывает `/monitor`;
- admin видит общий статус платформы;
- admin проверяет состояние runtime-компонентов;
- admin проверяет состояние scheduler;
- admin проверяет состояние telegram pipeline;
- admin проверяет состояние AI pipeline;
- admin смотрит backlog и деградации;
- admin видит alerts;

- admin открывает `/jobs`;
- admin видит summary по заданиям;
- admin просматривает pending jobs;
- admin просматривает dead-letter jobs;
- admin изучает статус выполнения задач;
- admin понимает, какие операции зависли или упали;
- admin запускает retry для проблемных задач;
- admin проверяет результат retry;
- admin использует jobs screen как центр операционного контроля асинхронных процессов.

### 20. Сквозной async job flow

- пользователь инициирует действие, которое не выполняется синхронно;
- система возвращает `job_id`;
- интерфейс начинает polling результата;
- пользователь видит, что действие выполняется;
- пользователь получает success/failure outcome;
- данные на экране переобновляются после завершения;
- пользователь понимает, завершилось ли действие успешно и какой объект был обновлен.

### 21. Read-only сценарии viewer

- viewer открывает dashboard posts/events/processes;
- viewer применяет фильтры и сортировки;
- viewer открывает детали поста;
- viewer открывает детали события;
- viewer открывает детали процесса;
- viewer читает существующие отчеты;
- viewer не видит actions на генерацию отчетов;
- viewer не видит actions на обновление комментариев;
- viewer не имеет доступа к keyword graph;
- viewer не имеет доступа к admin и platform разделам.

### 22. Операционные сценарии поддержки качества данных

- пользователь замечает partial dashboard state и продолжает анализ с учетом warning;
- admin проверяет monitor, если snapshot выглядит неполным;
- admin изучает jobs backlog, если отчеты или комментарии долго не обновляются;
- admin повторно запускает упавшие задачи;
- admin корректирует каналы или настройки, если данные перестали поступать.

- обновление комментариев постов;
- стабильная работа ingest/jobs pipeline;
- управление каналами как источниками данных;
- мониторинг и retry jobs для непрерывности сервиса.

Если формулировать короче, ядро бизнес-ценности — это `аналитика + отчеты`, а ядро операционной устойчивости — это `каналы + pipeline + monitor/jobs`.

## Главные пользовательские потоки

### 1. Вход в систему и попадание в рабочую область

**Стартовая точка**

- пользователь открывает `/login`.

**Шаги**

- вводит логин и пароль;
- отправляет форму входа;
- система валидирует учетные данные;
- создается сессия;
- пользователь перенаправляется в защищенную рабочую область, обычно на `/dashboard/posts`.

**Результат**

- пользователь аутентифицирован и может работать с доступными ему маршрутами.

**Возможные ошибки**

- неверный логин или пароль;
- backend auth недоступен;
- ошибка refresh/session initialization;
- у пользователя нет активной роли или доступ ограничен.

**Что считается успешным завершением**

- пользователь вошел в систему;
- сессия инициализирована;
- открывается первый доступный приватный экран.

### 2. Анализ постов и переход в детали поста

**Стартовая точка**

- пользователь находится на `/dashboard/posts`.

**Шаги**

- просматривает snapshot постов;
- применяет фильтры и сортировки;
- оценивает summary, `generated_at` и `warnings`;
- находит интересующий пост;
- открывает `/posts/:postId`;
- изучает метаданные, комментарии, связи и отчет.

**Результат**

- пользователь получает полную картину по конкретному посту и понимает, требует ли он дальнейшей работы.

**Возможные ошибки**

- dashboard не загрузился;
- список пуст по выбранным фильтрам;
- detail screen вернул ошибку;
- comments/links/report блоки не загрузились;
- snapshot частичный (`partial=true`) и часть данных недоступна.

**Что считается успешным завершением**

- пользователь нашел нужный пост;
- открыл детали;
- получил достаточно контекста для дальнейшего решения: продолжить исследование, обновить комментарии или запустить отчет.

### 3. Обновление комментариев поста

**Стартовая точка**

- analyst/admin находится на `/posts/:postId`.

**Шаги**

- открывает экран деталей поста;
- инициирует действие обновления комментариев;
- система ставит операцию в очередь и возвращает `job_id`;
- интерфейс poll-ит статус и результат job;
- после завершения обновляются данные поста и блока комментариев.

**Результат**

- комментарии поста актуализированы.

**Возможные ошибки**

- действие недоступно для текущей роли;
- mutation endpoint вернул ошибку;
- job зависла, завершилась с ошибкой или не вернула результат;
- Telegram pipeline недоступен или перегружен.

**Что считается успешным завершением**

- job завершилась успешно;
- пользователь видит обновленные комментарии и актуализированные метрики.

### 4. Генерация или обновление отчета по посту

**Стартовая точка**

- analyst/admin находится на `/posts/:postId` или в соответствующем report-контуре.

**Шаги**

- пользователь проверяет текущий статус отчета;
- запускает генерацию или обновление;
- система создает job;
- интерфейс отслеживает выполнение через jobs flow;
- после завершения блок отчета и связанные данные переобновляются.

**Результат**

- по посту появляется новый или обновленный отчет.

**Возможные ошибки**

- отчетная job завершилась ошибкой;
- AI pipeline недоступен;
- статус отчета не обновился после завершения job;
- пользователь не имеет прав на mutation.

**Что считается успешным завершением**

- отчет получил ожидаемый статус, например `draft` или `ready`;
- пользователь может открыть и прочитать актуальное содержимое отчета.

### 5. Анализ событий и работа с event graph

**Стартовая точка**

- пользователь находится на `/dashboard/events`.

**Шаги**

- просматривает список событий;
- применяет фильтры и сортировки;
- выбирает событие;
- изучает graph panel;
- просматривает связанные посты и статус отчета;
- при необходимости открывает `/events/:eventId` для полного контекста.

**Результат**

- пользователь понимает структуру события, связанные сущности и его аналитическую значимость.

**Возможные ошибки**

- dashboard событий не загрузился;
- graph payload недоступен;
- данные события частично деградированы;
- связанные посты не загрузились;
- detail route вернул ошибку.

**Что считается успешным завершением**

- пользователь выбрал событие;
- понял его контекст через граф и связанные посты;
- принял решение, нужно ли готовить или обновлять отчет.

### 6. Генерация или обновление отчета по событию

**Стартовая точка**

- analyst/admin находится на `/dashboard/events` или `/events/:eventId`.

**Шаги**

- выбирает событие;
- запускает draft report generation/update;
- система ставит задачу в jobs flow;
- интерфейс отслеживает выполнение;
- по завершении обновляются статус и содержимое отчета.

**Результат**

- по событию сформирован или обновлен draft-отчет.

**Возможные ошибки**

- job по отчету не выполнилась;
- граф или контекст события недостаточны для отчета;
- AI pipeline недоступен;
- mutation недоступна по роли.

**Что считается успешным завершением**

- отчет по событию появился или обновился;
- пользователь видит новый статус и актуальный аналитический текст.

### 7. Анализ процессов и работа с process graph

**Стартовая точка**

- пользователь находится на `/dashboard/processes`.

**Шаги**

- просматривает список процессов;
- применяет фильтры и сортировки;
- выбирает процесс;
- изучает иерархию процесса на графе;
- просматривает связанные события;
- при необходимости переходит в `/processes/:processId`.

**Результат**

- пользователь понимает, как устроен процесс, из каких событий он состоит и в какие постовые контексты ведет.

**Возможные ошибки**

- dashboard процессов не загрузился;
- граф процесса не построился;
- связанные события недоступны;
- detail screen вернул ошибку;
- данные частично деградированы.

**Что считается успешным завершением**

- пользователь увидел структуру процесса;
- понял цепочку связанных событий;
- может перейти к следующим аналитическим действиям или к отчету.

### 8. Генерация или обновление отчета по процессу

**Стартовая точка**

- analyst/admin находится на `/dashboard/processes` или `/processes/:processId`.

**Шаги**

- выбирает процесс;
- запускает генерацию или обновление отчета;
- система создает job;
- интерфейс отслеживает статус выполнения;
- после завершения обновляет данные процесса и report block.

**Результат**

- по процессу сформирован или обновлен отчет.

**Возможные ошибки**

- job завершилась неуспешно;
- AI pipeline недоступен;
- не обновился статус отчета;
- действие недоступно по роли.

**Что считается успешным завершением**

- пользователь получает актуальный process report и может использовать его в дальнейшей аналитике.

### 9. Просмотр и фильтрация каталогов отчетов

**Стартовая точка**

- пользователь открывает один из маршрутов `/reports/posts`, `/reports/events`, `/reports/processes`.

**Шаги**

- выбирает тип каталога;
- применяет фильтры;
- просматривает список отчетов;
- оценивает статусы и даты;
- переходит из каталога к нужной сущности или экспортирует результаты.

**Результат**

- пользователь быстро находит нужные готовые или черновые отчеты.

**Возможные ошибки**

- каталог не загружается;
- по фильтрам нет результатов;
- export недоступен или завершился ошибкой;
- viewer пытается выполнить недоступное action.

**Что считается успешным завершением**

- пользователь нашел нужный отчет или выгрузил нужный набор отчетов.

### 10. Пакетная генерация отчетов по постам

**Стартовая точка**

- analyst/admin находится на `/reports/posts`.

**Шаги**

- задает фильтры;
- запускает batch generation;
- система создает пакетную job;
- интерфейс отслеживает прогресс;
- после завершения каталог отчетов обновляется.

**Результат**

- сформирован пакет новых draft-отчетов по постам, попавшим в текущую выборку.

**Возможные ошибки**

- batch mutation завершилась ошибкой;
- часть отчетов не создалась;
- job зависла или попала в dead-letter;
- права пользователя не позволяют запуск batch flow.

**Что считается успешным завершением**

- пользователь видит обновленный каталог отчетов;
- нужное число отчетов создано или обновлено;
- итог задачи прозрачно понятен пользователю.

### 11. Исследовательский поток через keyword graph

**Стартовая точка**

- analyst/admin открывает `/keyword-graph`.

**Шаги**

- вводит поисковый запрос;
- задает фильтры по датам и каналам;
- запускает поиск по постам;
- получает результаты;
- выбирает seed posts;
- строит граф;
- изучает связи;
- при необходимости генерирует AI-отчет по графу.

**Результат**

- пользователь получает углубленное исследовательское представление по теме или набору ключевых слов.

**Возможные ошибки**

- поиск не дал результатов;
- граф не построился;
- отчет по графу оказался недоступен или слабого качества;
- модуль недоступен для текущей роли.

**Что считается успешным завершением**

- пользователь получил релевантные результаты поиска;
- построил полезный граф;
- смог извлечь из него аналитический вывод или отчет.

### 12. Добавление нового канала в систему

**Стартовая точка**

- admin находится на `/channels`.

**Шаги**

- открывает форму добавления канала;
- вводит данные канала;
- отправляет форму;
- система создает асинхронную job на подключение канала;
- admin отслеживает статус выполнения;
- после успеха канал появляется в каталоге и может участвовать в ingest.

**Результат**

- новый источник данных подключен к системе.

**Возможные ошибки**

- данные канала некорректны;
- Telegram pipeline не смог подключить канал;
- job завершилась с ошибкой;
- канал добавлен, но не активирован.

**Что считается успешным завершением**

- канал успешно создан;
- канал отображается в списке;
- канал может использоваться в основном data flow продукта.

### 13. Операционный контроль через monitor и jobs

**Стартовая точка**

- admin открывает `/monitor` или `/jobs`.

**Шаги**

- проверяет общее состояние платформы;
- оценивает runtime, backlog, alerts и деградации;
- переходит в jobs;
- просматривает pending и dead-letter задачи;
- при необходимости выполняет retry;
- повторно проверяет состояние системы.

**Результат**

- admin понимает текущее операционное состояние платформы и может снять инцидент или деградацию.

**Возможные ошибки**

- monitor snapshot не загружается;
- jobs API недоступен;
- retry не сработал;
- проблема глубже и требует изменения настроек, каналов или runtime.

**Что считается успешным завершением**

- причина деградации выявлена;
- проблемные jobs обработаны;
- система возвращается в рабочее состояние или становится понятен следующий шаг для восстановления.
